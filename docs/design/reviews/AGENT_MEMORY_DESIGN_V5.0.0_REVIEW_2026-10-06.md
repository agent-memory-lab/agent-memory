# Agent Memory v5.0.0 完整性与逻辑性审查

审查日期：2026-10-06<br>
审查对象：[统一架构设计 v5.0.0](../AGENT_MEMORY_DESIGN_V5.0.0.md)<br>
对象状态：PROPOSED_BASELINE<br>
设计正文 SHA-256：`83330a5c8e7921aa56ea76afbb9e8a9b255a5a22732ae4f7c20816deaf25517f`<br>
审查性质：设计静态审查；不是运行时漏洞验证、故障注入或生产验收。本文不改变原设计契约。

## 1. 结论

**方案在职责覆盖和总体方向上较完整，但跨模块、跨操作的契约还没有全部闭合，不宜把它直接视为可以逐章实现的最终规格。**

已经成立的主干是：有来源的候选 → 独立的保真/价值/资格判断 → 有证据与版本的 L1 → 可失效的派生知识 → 按用途受控读取。双时态、模型提议与内核发布分离、L0–L3、可靠任务、删除和迁移之间没有发现需要推翻整体架构的直接矛盾。

主要问题发生在组合操作：多个范围同时适用、同一来源重新解释、证据只覆盖部分字段、替换后撤回、跨槽纠错、派生生成期间新增事实、生成期间权限变化。单独阅读各章节时合理，组合执行时却可能出现两种不同的合法理解。

本次归纳 **13 项修订建议：4 项 P1、9 项 P2**。P1 表示在启用相关能力前应优先补齐的正确性或数据边界契约；P2 表示必须在对应阶段验收前明确的组合语义或运行保证。数量不表示现有代码已经存在相同数量的漏洞。

| 维度 | 判断 | 依据与局限 |
| --- | --- | --- |
| 产品边界和模块职责 | 较完整 | 宿主、内核、插件、存储、整理与检索职责明确；模块化单体符合当前项目规模 |
| L0–L3 的组织模型 | 合理 | L0 来源、L1 可维护断言、L2 场景、L3 长期偏好/推断分离；Observation 是整理组件而非强制第五层 |
| 抽取与接纳判断 | 主流程完整，部分核验状态机不足 | 已分开保真、价值、资格和用途；尚缺受支持部分如何生成正式断言的统一规则 |
| 双时态 | 基础定义成立，操作组合需补齐 | 有效时间与系统时间分离；替换、撤证、跨槽纠错及历史派生的组合仍有未定语义 |
| 核验与证据 | 范围建模合理，发布契约需细化 | 不把工具成功、模型分数或来源数量当真值；需定义多证据联合支持及必要字段集合 |

| 派生与增量维护 | 方向完整，负面/集合结论依赖不足 | 已有修订依赖、订阅和水位；“无阻塞”“全部完成”等需要查询覆盖依赖 |
| 权限与删除 | 原则充分，生成输入/最终输出需收紧 | 已有今天的访问约束和删除屏障；必要引用集合不能替代实际生成输入集合 |
| 验收与演进 | 覆盖面较广，最终效用门槛不足 | 抽取门槛、故障矩阵和对照实验已定义；最终检索与任务退化目前主要要求报告 |

不以“章节很多”判定可实施性。每项能力还需要明确输入、状态转换、事务边界、输出承诺、失败结果，以及与其他操作组合后的答案。

## 3. 优先修订问题

### R01 / P1：跨适用范围的状态合成规则缺失

**定位：** 原设计第 302、360、578、894–900 行。

slot 身份包含 scope，冲突主要在同槽内处理；读取又允许用户、项目和会话相关记忆共同参与。四类范围虽然已经区分，尚未定义同一逻辑属性在多个适用范围下如何合成。

**反例：** 用户长期偏好中文，项目 A 明确要求项目沟通用英文。两个不同 scope 的单值槽都能接纳。项目 A 的查询应当使用哪一个、是否属于覆盖、例外或争议，不能由相关性分数或返回顺序决定。

**建议：** 分开隔离身份与适用范围；引入可信查询上下文。PredicateSpec 声明哪些范围可继承、哪些可以覆盖、哪些必须共同满足、不可比较时如何返回歧义。不能全局硬编码“越具体越优先”，例如个人偏好不能覆盖组织强制约束。

**验收：** 用户/项目/会话偏好与团队约束组合矩阵；交换检索顺序后结果相同；权限不足的范围不参与事实合成且不泄漏其存在。

### R02 / P1：reprocess 没有定义新旧解释的替代关系

**定位：** 第 267–272、630–632、957 行。

新 batch/generation、版本关联和来源族复用已规定，但旧一代已发布解释何时保留、撤回或替换没有确定规则。

**反例：** 旧抽取错误地产生“居住上海”，新策略对同一来源得到“居住杭州”或零候选。只新增会保留旧误提或制造伪争议；按候选缺席撤回，又可能让一次漏提或截断清掉合法旧解释。

**建议：** 明确追加处理与替代解释两种模式；保存覆盖清单、完整性和旧新候选映射。替代模式原子重评估受影响的旧解释与新解释。partial、失败和候选缺席不得隐式等同于反证。其他独立来源仍支持的结论应按幸存证据重评估。

**验收：** 同源重处理的同值、更正、零候选、partial、失败、多来源共同支持；全过程无双重计数和短暂伪确定状态。

### R03 / P1：模型输入和答案交付缺少明确的权限检查边界

**定位：** 第 825–827、864–869、929–930 行。

检索前置过滤写为“尽量”，最终权限检查位于精排之后。Reflect 限制引用来自本轮读取集合，但未规定读取之后、答案交付之前发生撤权或擦除时如何处理。全局不变量虽要求访问与删除约束，具体生成流程还不能保证实现者在正确位置执行它们。

**反例：** 旧索引取回已撤权正文，外部重排服务先收到内容，之后才被最终守卫过滤；或者 Reflect 合法读取后生成 30 秒，其间来源被擦除，最终仍交付旧内容。

**建议：** 将正文进入模型/外部精排前的授权、存活和允许处理范围检查设为硬门槛。记录实际读取依赖及访问/删除代次；生成完成后再次检查，撤销后丢弃相关产物或重新生成。定义读取/交付的线性化点；流式输出明确授权截止点及发现失效后的停止行为，不承诺追回已交付字节。

**验收：** 在候选读取、外部调用前、模型运行中、答案交付前分别撤权或擦除；检查供应商实际输入与最终输出，不能只测试最终 Bundle。

### R04 / P1：派生权限不能只由“必要引用”决定

**定位：** 第 730–731、760–762、904–906 行。

“所有必要依据受众的交集”适合描述证明资格，但无法独自覆盖生成过程读取过的全部敏感内容。模型选择的引用集合可能比实际输入集合小。

**反例：** 模型同时读到公开资料与管理员私有信息，答案受到后者影响，却只列公开资料为必要引用。按现有规则，派生受众可能扩大到团队。

**建议：** 分开事实支持依赖与信息处理依赖。默认按本次实际提供给生成器的全部来源传播访问约束；必要/可选证据只影响证明和重评估，不自动免除信息权限。扩大受众走原设计已定义的独立脱敏/级别转换政策和新产物流程。输入清单由内核记录，不依赖模型自报。

**验收：** 私有材料无引用、被标成可选依据、生成后撤权等情况；公开受众不能据此获得未经批准的派生内容。

## 4. 需要补齐的组合契约

### R05 / P2：字段级核验与候选整体接纳之间缺少状态机

**定位：** 第 317–324、460、471、490–500、958、1268–1273 行。

**反例：** 候选为“订单 A 在 10 月 1 日已付款 100 元”；工具只证明 10 月 3 日 `paid=true`。整体 ACCEPT 会带入未核验金额/日期；整体待决又无法使用已证明的当前状态。

**建议：** 各类型声明必要语义字段集合和允许拆分的语义单元；在同一目标坐标验证联合证据，必要时按业务契约核对业务修订/观察组。支持范围不能因拼接扩大。允许新建独立的“10 月 3 日观察到已付款”解释，并保持原金额/日期待决；条件、例外和主体等必要限定不能为通过核验而删掉。明确替代支持与联合支持，以及撤回其中一项后如何重新计算资格。

**验收：** 部分字段通过、不同时间证据、同一来源族重复、替代证据幸存、条件/例外缺证据。

### R06 / P2：替换后撤证时，旧状态是否恢复未定义

**定位：** 第 499、564–571 行。

**反例：** 杭州从 t0 成立，上海从 t1 真实替换；随后撤回上海的证据。仅按幸存断言重算可能恢复杭州，但失去上海的支持不等于证明杭州仍成立。如果被撤销的是整次错误搬迁解释，重算又可能应恢复杭州。

**建议：** 状态终止边界/变化决策自身记录依据与修订。区分失去新值支持、撤销错误替换决策、现实再次变化。新值失去支持不能自动复活旧值；只有明确更正或合格依据支持时重算边界。

**验收：** 替换后撤证、更正替换时间、撤销整次替换、来源擦除、终止依据独立幸存的 valid/known 查询矩阵。

### R07 / P2：同槽更正不能覆盖主体或谓词提取错误

**定位：** 第 302、366–376、426、566、586–588 行。

**反例：** “工作地址杭州”误存为家庭地址，修复跨两个槽。普通实体合并/拆分不能解决谓词错误，分别撤回和新增又缺少统一更正身份与原子结果。

**建议：** 保留同槽更正的保护，增加显式的跨槽更正组合：撤回旧解释、创建新解释、记录替代关联、同步失效相关派生。校验两个槽的权限与预期版本，原子提交。不支持时在能力声明中拒绝。

**验收：** 改主体、改谓词、改身份限定；跨槽权限不满足及并发更正时整项失败；历史不被回写。

### R08 / P2：集合与否定性结论缺少查询覆盖依赖

**定位：** 第 773、800–802、1287–1289 行。

设计已经考虑按主体、slot、facet 和订阅范围处理新事实，不能说完全没有新增事实失效机制。缺少的是它与当前完整性声明及发布屏障的关系。

**反例：** 快照 100 的“项目所有未完成任务”查询生成“没有阻塞”；生成期间 101 新增阻塞，已有父修订均未变化。仅检查引用依赖可允许发布 100 的页面，尚未确定它是否能标为当前 ready。

**建议：** 集合、计数和否定结论记录 query/facet 订阅代次、覆盖范围及已处理水位。新增成员、移出成员、资格变化同样推进相关代次。发布必须检查；落后产物可以标明 as_of，但不能宣称当前完整。无需为每个无关新事实重建全库。

**验收：** “无阻塞”“全部完成”“唯一负责人”等结论生成期间新增/移出成员；无关范围的新事实不触发全库刷新。

### R09 / P2：历史派生资格与今天的安全屏障需要分开计算

**定位：** 第 540–541、764–771 行。

今天的访问/擦除限制已经明确。缺口在于读取守卫如何同时处理历史依赖有效性与当前安全代次。

**反例：** K10 页面依赖 A1，K20 更正成 A2。读取 known_at=K15 时，若只比较当前父代次会误拒历史页面；若全部回到 K15 检查则可能漏掉今天的擦除。

**建议：** 普通更正、争议与有效期按查询 valid/known 坐标判断；访问、擦除和强制保留限制按当前状态判断。失效原因和系统生效边界分别可识别。相关实现仅在声明 derived_historical_views 时成为启用前置条件。

**验收：** 普通更正后历史仍可重现；当前撤权/擦除后所有历史访问遵守当前屏障。

### R10 / P2：事务 A 前请求缺少生命周期入场凭证

**定位：** 第 606–608、935–936、1278–1283 行。

**反例：** R 已收到正文但在事务 A 前排队；scope 从 12 擦除到 13；R 首次查库取得 13 后提交。仅检查当前 generation 无法区分它与真正的新请求。

**建议：** 定义请求被系统接纳的时间点及可信 admission ticket，携带入口 scope epoch，在事务 A 比较。旧请求不能自动读取新 epoch 升级。若承诺仅覆盖已取得入场凭证的请求，应明确收窄原文“已经开始”的含义；擦除后新输入的进入政策也需声明。

**验收：** 请求在入口、排队、事务 A、worker 各阶段遭遇 scope 擦除；允许的新输入能取得新身份，旧请求不能复活。

### R11 / P2：接收回执与事实发布的 commit token 混用

**定位：** 第 607–615、621、698–699、967–983 行。

**反例：** durable 返回 queued/token=100，索引已到 100，但抽取未结束，L1 尚未发布。用该 token 要求 read-your-writes 可以立即结束，却读不到新事实；这不一定属于索引落后。

**建议：** 区分 capture_commit_token 与 publication_commit_token；status 返回实际发布版本。after_batch 等待条件区分处理终态、事实发布、指定索引可见。待核验、partial、处理失败和索引滞后单独报告；索引水位代表连续覆盖而非见过的最大序号。

**验收：** 仅接收、发布未索引、索引追平、待核验、零接纳、批次部分完成；无虚假的“已读到写入”。

### R12 / P2：共享硬预算缺少并发预留和结算协议

**定位：** 第 1004–1006、1016–1020、1028 行。

**反例：** 剩余租户预算只够一次调用，十个 worker 同时检查余额并调用。每个请求满足自身限制，总额却突破硬上限。

**建议：** 声明共享预算的原子预留、结算、释放与幂等规则；重试、并发败者和未确定完成的调用都占用相应额度，不能仅因租约到期立即释放尚可能产生费用的预留。严格费用能力需要可约束的计费上界；只有估计时明确保证范围，不将费用未知视作零。

**验收：** 多 worker 抢最后一份额度、调用后崩溃、供应商回执丢失、重试重复计费与结算重放。

### R13 / P2：最终检索与任务效果缺少可阻断发布的门槛

**定位：** 第 1094–1102、1113–1114、1178 行。

**反例：** 抽取满足 precision≥97%、recall≥85%，但检索过滤/排序使有效记忆几乎不返回。系统仍可满足无误写和预算约束，并仅报告召回变差。

**建议：** P0 固定每种用途的 Recall@budget 下限、相对基线允许退化幅度，以及任务质量/成本门槛。未达标阻止对应能力默认启用。数值可以由领域配置确定，但必须从“报告”变成“验收条件”。无法建立可靠效果样本时继续实验性开放。

**验收：** 抽取良好但最终召回退化的版本必须被挡住；新增 Observation/Reflect 的收益与成本在相同预算/样本下比较。

## 5. 对架构和开发顺序的建议

保留现有模块化单体与 L0–L3 主干，不为每个审查项拆一个服务、目录或存储。修订落在已有职责中：

| 现有职责 | 需要补齐的契约 |
| --- | --- |
| domain / ontology | 适用范围合成、必要字段、证据组合、终止边界和跨槽更正 |
| consolidation / admission | 部分核验状态机、重处理代替规则、合格解释发布 |
| operations / storage | 入场 epoch、分阶段 token、原子预算、事务与任务恢复 |
| retrieval / context | 当前/历史两类守卫、模型输入校验、查询覆盖、交付前检查 |
| consolidation / derived views | 输入权限传播、证明与处理依赖分离、增量失效 |
| evaluation | 组合场景金标准、检索和任务非退化门槛 |

建议按以下顺序关闭问题：

1. **先定语义契约。** R01、R02、R05、R06、R07，形成状态转换表及查询期望；避免带着歧义冻结 schema/API。
2. **完成最小纵向闭环。** 支持有限谓词的采集、抽取、接纳、双时态读取、更正和删除，同时交付必要的读端守卫。P5 中与正确性有关的读取能力应随前期写入能力一起验收，不能全部等到后期。
3. **扩展 durable。** R10、R11、R12 与事务/租约故障测试一起交付，支持显式同步模式继续工作。
4. **再启用 Observation/L2/L3。** R04、R08 是基础；R09 随历史派生能力交付。R03 的模型输入检查在第一次启用外部抽取/重排时就需要，Reflect 交付检查随 Reflect 一起完成。
5. **全过程执行效果门槛。** R13 在 P0 冻结协议，各期按已声明用途验收；任务收益不等最后阶段才评估。

## 6. 版本处理

保留 v5.0.0 作为此次审查的固定基线。先给每项问题分配修订决策、所属能力和验收用例，再发布新设计文件。

如仅澄清现有不变量并兼容增加可选契约，可按仓库规则发布 5.0.1 或 5.1.0；如果决定改变核心 slot 身份、时间解释、权限或已发布 API 语义，则需按原设计第 32.4 节评估 6.0.0 和迁移。不要在尚未确定修订内容时直接承诺所有变化都属于 minor。

模型供应商、画像阈值、保留期、领域谓词目录和新鲜度数值已列为待校准配置，本次不把这些再列为设计缺陷。已实现/目标能力的清晰区分应继续保留；无需因尚未实现全部目标而否定方案。
