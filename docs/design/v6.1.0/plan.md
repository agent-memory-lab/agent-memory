## 1. 交付目标

把现有 Agent Memory 扩展为具有可靠接入、明确事实资格、双时态解释和可维护派生知识的记忆组件。
每项能力从写入到读取都必须可追溯，遇到证据不足、冲突、权限变化和处理失败时有确定结果。

核心数据流：

```mermaid
flowchart LR
    Host[宿主消息与工具回执] --> Capture[可信捕获与待发]
    Capture --> L0[L0 来源与任务原子接收]
    L0 --> Admission[抽取、判断与必要核验]
    Admission --> L1[L1 双时态事实解释]
    L1 --> Read[按用途检索与交付]
    L1 --> Obs[可选 Observation]
    Obs --> View[L2 场景与 L3 长期知识]
    View --> Read
    Read --> Reflect[可选只读 Reflect]
```

身份、权限、生成输入谱系、删除屏障和预算贯穿主链。评测沿捕获、抽取、检索、装包和宿主结果归因。
L0 是来源依据，L1 决策账本定义系统采用的解释；索引、Observation 和文档均是可重建投影。

### 1.1 首个可交付闭环

先选择少量已登记且有金标准的谓词，例如语言偏好、项目约束、明确决定/计划和工具执行结果。
首批最终范围由 T01/T02 的差距审计和契约确定；不声称这四类复杂语义一次全部支持。

一个宿主通过 SDK 接入后，应能完成：

1. 可信捕获并可靠接收来源，重复投递不形成重复独立证据。
2. 分别判断语义支持、记忆价值、来源资格、适用时间和核验需要；待决不混入默认事实。
3. 发布带来源定位的 L1 解释，按 `valid_at` 与 `known_at` 查询。
4. 完成更正、真实替换、撤回和必要争议处置；没有合格支持时明确未知。
5. 查询有限处理目标的阶段状态，区分“来源已收”“已决策”“索引可见”。
6. 验证崩溃恢复、权限撤回和擦除，旧任务及索引不能复活已删内容。
7. 在固定数据、权限和预算下报告质量、覆盖、延迟及成本；通过启用能力对应门槛。

首个闭环由 P1 和所需 P2 联合交付。P1 的语义原型可先用确定性适配器验证；需要外部模型的生产路径，
必须先具备所需 L0 持久化、输入/交付守卫、预算和删除协议。未具备的严格能力不对外声明。
所有生成型 L1 首次启用前，T25 的适用 processing 依赖与输出权限计算切片均须完成，单来源同样适用；
T36 的模型输入上限同样在首次模型启用前验证，不能因任务归入 P3/P5 而后置。
已有旧协议继续按既有能力运行，不能在开发中静默换成未验收的新语义。

### 1.2 后续扩展

P3/P4 提供带依赖与失效规则的 Observation、场景文档及长期画像；P5 加强检索与可选 Reflect；
P6 处理达到实际规模后需要的索引迁移，以及多模态、可移植导入导出、Procedure 演化等可选能力。
模型训练、通用 Agent 编排、控制台扩建、强制图数据库不属于本计划的核心交付条件。

“后续扩展”不延后已有能力的正确性：读取从首次启用起不得静默截断，向量空间不能混用；
基础备份、崩溃恢复和擦除日志验证在 T23/T24 完成。派生历史查询和跨槽更正可明确声明不支持，
但已启用的 L1 双时态、同槽更正/撤回与当前安全守卫仍须完整验收。

## 3. 实施原则与发布边界

1. 每次开发提交一段可验证行为：接口、持久化、读取、失败、权限和必要迁移一起交付。
2. 所有新能力先协商，旧 JSON/API 使用显式投影；新增默认字段不自动证明协议兼容。
3. L0 与处理请求原子接收；接纳与解释发布使用明确事务；网络调用不在数据库锁内等待。
4. 输入、模型派发、发布和最终交付分别执行需要的当前安全检查，记录可解释的顺序边界。
5. 支持依赖与全部实际生成输入分开；省略引用不能放宽受众，撤证不能自动证明相反命题。
6. 凡声明双后端共同支持的能力，必须以 SQLite 和真实 PostgreSQL 验证；缺环境记未验证。
7. 抽取、检索和任务收益分别衡量；相关性分数、来源数量和历史跑分不能替代资格或发布验收。
8. 不支持的组合显式拒绝；能力关闭、合理拒答、系统错误与覆盖不足分别报告。

### 4.1 并行工作与会合点

- **语义线**：T06–T14；先完成可被确定性数据验证的候选、证据和时间规则。
- **可靠性线**：T15–T24；以现有有限 Atom 类型接入，不等待所有复杂语义实现。

## 6. 验证策略与完成定义

### 6.1 证据层次

| 检查层 | 验证重点 | 不能替代 |
| --- | --- | --- |
| 确定性语义测试 | 条件/例外、AND/OR 支持、跨范围、双时态、更正与撤回 | 模型在真实数据上的抽取能力 |
| 存储/并发合同 | 原子性、CAS、租约栅栏、query 屏障、入口 epoch、预算与恢复 | 单进程 mock 成功不能替代真实后端竞争 |
| SDK/MCP/宿主集成 | 可信身份、序列化、旧协议、能力拒绝和状态查询 | 内核直接调用通过不代表宿主可用 |
| 冻结检索基线 | 固定 L1/索引、证据覆盖、充分支持、预算与 trace | 不能解释采集或抽取质量 |
| 端到端基线 | 原始事件到任务结果，涵盖阶段失败、费用和延迟 | 合成 17 事件/20 检查不能替代领域真实数据 |
| 运维与迁移 | 升级、停机恢复、删除日志重放、旧数据降级和恢复边界 | 构建或导入成功不能替代数据恢复 |

设计第 25.6/25.9 节的 66 项是必要验收规格，尚不是 66 项已存在或已通过的自动测试。
每个用例绑定任务、代码/数据/配置版本、实际命令或可复现步骤、结果与日志位置。
跨租户、擦除泄漏、关键语义反转等合同失败阻断相关能力；覆盖和任务质量不能靠全部拒答满足。

质量与成本数字由冻结 AcceptanceProfile 管理，缺数据或缺阈值时保持实验性；不在计划里编造工期、SLO或跑分。
模型输出保存版本与必要审计信息，重复采样报告波动；任何结果采集仍受权限、保留和擦除约束。

### 6.2 单任务完成定义

- 行为和失败语义满足所引用设计；接口、状态、输出字段均已实现或明确拒绝。
- 相关自动测试、必要真实后端与宿主验收有证据；失败、跳过、未知单列。
- 数据/协议兼容、配置、可观测性和必要迁移有说明；核心无新增强制可选依赖。
- 触及读取、更正或删除的改动同步覆盖相应路径；不能留给后期“补安全”。
- 在 task.md 记录提交/PR、验收版本及证据位置后才由 `[ ]` 改为 `[x]`。

## 7. 数据、协议和部署迁移

1. T01/T02 识别旧数据缺少的字段和保证，形成迁移矩阵；不从引用列表伪造完整生成输入谱系。
2. 新增结构、索引和协议投影，保持旧入口的既有含义；无法迁移的内容显式标记能力不足。
3. 以 shadow 模式比较有限能力，隔离候选和派生物，不改变正式事实或扩展受众。
4. 在所需 R/N 和领域质量门槛通过后，按 capability/租户/用途启用 enforced 模式。
5. 若退化则停止相关新写入或回退检索策略，保留已提交认知版本和审计；回滚不得绕过已发生的擦除。
6. Schema 不可逆变更先给出兼容旧代码的限制与恢复方案，不能依赖启动旧二进制“自动回退”。

旧 CaptureProfile 完整性、入口票据、query 历史和费用不能追溯伪造。旧视图缺依赖时重建或仅按明确 as_of 使用。
向量模型变化生成新空间和索引代次，验证水位、删除日志与质量后切换；同维度不允许混用。
默认不迁移旧租约、在途未知外部调用或已失效授权为新的可执行工作。
