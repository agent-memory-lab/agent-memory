# Agent Memory v3 记忆进化与 Agent 扩展方案

更新日期：2026-09-11

本文补充《Agent Memory 插件化架构与实施方案 v3》的第 13、14、16 节，明确记忆进化、Agent 训练和运行编排之间的阶段关系。本文是设计与实施路线，不代表所列接口或能力已经实现。

## 1. 产品定位与最终目标

Agent Memory 的核心产品是一个可插拔、证据驱动的进化型记忆插件，将执行轨迹转化为版本化状态、情节记忆和可复用过程候选，提供受控整理、检索、评估记录、晋升与回滚。

项目的最终路线还包括记忆驱动的 Agent 训练与运行编排。这些能力在记忆闭环稳定之后交付，通过独立扩展复用记忆证据、评估接口和版本体系。基础插件始终可以独立安装和使用。

产品分为三个层次：

| 层次 | 负责的对象 | 执行位置 | 引入阶段 |
| --- | --- | --- | --- |
| Memory Core | Event、Claim、Current State、Episode、MemoryBundle | 宿主进程或存储服务 | 基础阶段 |
| Memory Evolution | 反馈、整理策略、检索策略、Procedure 候选与生命周期 | 可选插件及后台任务 | 近期重点 |
| Agent Evolution Extensions | 模型训练、Prompt 与 Harness 候选、运行编排、Agent 版本发布 | 独立工作进程或外部服务 | 最后阶段 |

依赖方向为扩展依赖稳定协议，内核不依赖训练或编排框架。训练服务或控制平面停机时，基础写入和检索仍可使用。

## 2. 从自进化体系吸收到记忆设计的机制

| 机制 | 在记忆插件中的用途 | 最后阶段的复用方式 |
| --- | --- | --- |
| 执行轨迹与结果关联 | 将记忆引用、决策、工具结果关联为 Episode | 形成训练样本与失败案例 |
| 版本化评价标准 | 解释反馈来源及适用范围 | 比较模型、Prompt 和 Harness 候选 |
| 实验与基线记录 | 比较检索策略和 Procedure 的收益 | 比较 Agent 版本及编排方案 |
| 候选、评测、晋升与回滚 | 控制记忆策略和 Procedure 生效 | 控制 Agent 配置和模型版本上线 |
| 可重放的数据快照 | 复现检索与记忆整理结果 | 构建可重复的训练和离线评测 |
| 成本及资源预算 | 限制候选数、Token、后台工作量 | 限制训练费用、运行步数和工具调用 |
| 失败经验与反例 | 保存适用边界，避免重复错误 | 提供纠错样本和偏好对比 |

这些机制可以共用标识、审计和证据引用，但不同对象保持独立生命周期。任务失败不等于某条记忆错误；Procedure 被拒绝不等于其来源事件需要删除。

## 3. 统一证据与反馈闭环

建议关联结构如下，具体字段在实施时与已有领域模型合并，避免重复定义：

```text
Trajectory / Event
    -> Claim / Current State / Episode
    -> RetrievalTrace + MemoryBundle
    -> DecisionRecord
    -> OutcomeEvent + EvaluationRecord + RewardSignal
    -> MemoryChangeProposal / ProcedureCandidate / PolicyCandidate
    -> EvaluationRun + PromotionRecord
    -> Active version or RollbackRecord
```

Event 可以分别支撑不同派生物，不要求所有事件依次经过所有类型。原始证据保持追加式记录；修正通过版本、撤销和替代关系表达。真删除仍优先于历史保留要求。

| 记录 | 必需信息 | 关键约束 |
| --- | --- | --- |
| RetrievalTrace | request_id、bundle_id、候选与返回项的 ID/版本、policy_version、预算和裁剪原因 | 记录返回项不等于证明实际使用 |
| DecisionRecord | run_id、decision_id、bundle_id、已确认使用的记忆引用、action_ref | 宿主未报告使用情况时标记 unknown |
| OutcomeEvent | outcome_id、decision_id 或 run_id、结果、终止原因、成本 | 区分成功、失败、取消与未知 |
| EvaluationRecord | evaluator_id/version、rubric_id/version、指标、证据、时间 | 模型自评应带来源标签，不自动获得权威地位 |
| RewardSignal | evaluation_id、reward_definition_id/version、数值、单位或归一化信息 | 不同定义的奖励不可直接合并 |
| EvolutionRun | baseline/candidate 版本、数据快照、评测配置、状态 | 只用完成且有效的评测推动晋升 |

接入层从认证上下文派生 Trusted Scope，拒绝模型自行扩大作用域。所有反馈写入支持幂等、延迟到达、重复到达和更正记录；缺失评价不能按零分或失败处理。

奖励定义权由宿主或其明确配置的评价组件持有。最后阶段可以提供 RewardProvider 实现，按宿主批准的公式执行计算，并记录公式版本及输入证据。

记忆被返回、被引用、与成功相关，是三种不同强度的证据。只有设计合理的对照实验才能支持因果收益结论。先保存可分析数据，再以无记忆、固定记忆策略和候选策略为基线开展对照。

## 4. 记忆内部的进化行为

### 内容与结构整理

合并重复 Claim 的来源，使用 supersession 管理事实变更；从完整任务生成 Episode，保留失败原因与反例；从多条有结果支撑的 Episode 提炼 Procedure 候选。每次提炼记录提取器版本、证据范围与适用条件。

低价值和过期内容可以降权或归档。冲突事实应进入冲突处理，不能仅因多数轨迹出现同一答案就覆盖可信 Current State。派生物权限不能比来源更宽；来源删除后，清理或重新计算受影响派生物。

### 检索与预算策略

先提供确定性且版本化的通道权重、时效权重、失败经验权重和 Token 分配规则。后台依据有效反馈生成候选参数，限制每次调整幅度，并保留固定策略作为回退。

检索策略不得调整租户权限、证据有效性或调用方总预算。关键状态超过预算时，返回明确的不足状态和裁剪说明，不得默默突破预算。调用方决定是否扩大预算或继续执行。

样本不足时沿用已批准策略。全局或跨租户学习须单独授权，默认只在明确的作用域内聚合。无反馈任务、取消任务和评估器异常任务不进入成功率分母。

### Procedure 生命周期

```text
candidate -> evaluated -> shadow -> canary -> active
active -> superseded / rolled_back / archived
failed evaluation -> rejected or revised candidate
```

每次迁移校验对象版本、来源有效性、评价策略版本、宿主授权及对应门槛。默认不允许候选跳过必要门槛；宿主批准的替代评测流程必须显式版本化并留下审计记录。

shadow 和 canary 在基础插件中表示状态、分组和证据记录。真实工具执行、流量分配及外部副作用由宿主执行；最后阶段可由宿主授权的编排扩展执行。回滚切换生效版本并停止新分配，无法撤销已经发生的外部副作用。

## 5. 预留接口与安装边界

以下为逻辑端口建议，不能作为当前可调用 API 文档：

| 端口 | 职责 | 基础安装行为 |
| --- | --- | --- |
| FeedbackPort | 摄入 Outcome、Evaluation、Reward 并校验引用 | 可选启用 |
| EvaluationPort | 运行宿主配置的记忆评测或接收外部结果 | 无配置不自动评价 |
| PromotionPolicyPort | 根据策略与审批校验版本晋升 | 无策略不自动晋升 |
| DatasetExportPort | 输出经过授权的轨迹样本和快照清单 | 按请求分页或流式导出 |
| ArtifactRegistryPort | 管理对象摘要、版本、兼容性与生效指针 | 核心只保存引用与必要元数据 |
| TrainingPort | 提交训练任务，读取状态，取消任务，返回制品引用 | 最后阶段独立安装 |
| RuntimeOrchestrationPort | 按授权执行候选运行、预算控制及流量分配 | 最后阶段独立安装 |

保留 `ingest/retrieve/state/propose/forget/capabilities` 主协议。扩展通过 capability 和协议版本协商启用。大体积训练集、模型权重、完整运行日志存放在外部制品存储，核心保存受访问控制的引用；不得在制品引用中持久化明文凭据。

源码敏感扫描和包构建验收属于开发发布工具，不进入记忆热路径。训练框架、GPU 运行库和编排调度器不加入基础包依赖。

## 6. 最后阶段的 Agent 训练与运行编排

### 训练数据与方法

先实现数据快照与导出，再接入训练任务。快照包含来源及派生关系、数据许可、删除状态、版本、时间范围、作用域、脱敏策略和 train/eval/test 切分标识。数据集按任务组及时间切分，避免相似轨迹同时进入训练和评测。

Episode、Procedure 候选与模型自生成总结不能直接视为正确标签。训练样本须满足相应质量策略，保留失败样本和反例。同任务下经过可信评价的候选对可供偏好学习使用。

默认实施顺序为样本导出、SFT 或偏好训练适配，再根据业务证据决定是否接入 DPO、PPO、GRPO 等方法。算法名称不构成交付要求或先进性证明；选择依据是反馈形式、样本质量、实验收益及资源成本。所有训练在独立环境完成。

撤销来源时停止新的导出及受影响制品晋升，对已生成的数据集和模型标记受影响状态。删除训练数据不能保证已训练模型遗忘，需记录影响范围并按宿主策略停用、重训或采用经验证的遗忘方法。

### 运行编排

编排扩展消费版本化 Agent 配置、模型引用、Prompt、工具许可、路由及 Workflow 定义，执行受预算限制的任务，并将 Decision、Outcome 和 Evaluation 回写记忆层。

首个版本只支持一个宿主的单 Agent 候选运行及版本比较。随后按实际需求增加路由、工作流和多 Agent 协作；避免把通用多 Agent 平台作为首个交付条件。

优化流程输出配置提案，经过离线评价和宿主批准后才进入 shadow/canary。执行器校验可用工具、资源预算、终止条件及制品兼容性。训练完成不自动发布，发布成功不自动扩大权限。

每次发布绑定 Agent 版本、模型版本、Prompt/Harness 版本、MemoryPolicy 版本和 Procedure 集合版本。回滚选择兼容的版本组合，避免只回滚模型而继续使用不兼容的新流程。

## 7. 分阶段实施与验收

沿用 v3 P0-P6 的协议、内核、存储、接入、控制台与治理安排。P7-P9 调整如下，并新增最后阶段 P10。发布准备可并行推进，不必等待全部高级能力完成。

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| P7a 反馈关联 | RetrievalTrace、Decision/Outcome/Evaluation/Reward 关联及幂等 | 重复、乱序、更正和缺失反馈处理正确；作用域不可越权 |
| P7b 记忆整理 | Episode、Procedure 候选、版本化整理提案 | 来源完整、失败经验保留、删除传播和并发更新有验证 |
| P7c 受控记忆进化 | 检索策略候选、评测、生命周期及回滚 | 宿主门槛不可绕过；回放可复现；未知结果不会被计为成功 |
| P8 可选高级记忆 | Graph、latent、学习型记忆策略及数据导出 | 每项可关闭；相对基线收益有证据；不破坏来源和预算 |
| P9 分版本发布 | 安装、文档、CI、真实后端验收及资源报告 | 新环境可复现；扫描失败或未完成不得被报告为通过 |
| P10a 训练扩展 | 快照、TrainingPort、训练任务与制品登记 | 无数据越权或评测泄漏；任务可取消；制品可追溯 |
| P10b 编排与发布扩展 | 单 Agent 候选运行、配置比较、灰度及版本回退 | 权限、预算、审批和停止机制有效；反馈完整回写 |
| P10c 联合优化 | 在有证据的任务上协同优化记忆与 Agent 策略 | 有独立留出集及消融对照；成本可接受；版本可回退 |

P10 以 P7 的反馈可信性、P9 的相应发布门槛为前提。Graph 和 latent 不是训练或编排的强制前置条件。

所有阶段分别报告无记忆基线、固定策略和候选策略的效果、样本量、评估器版本、费用及延迟。收益阈值由宿主指定，不在插件中预设通用成功标准。

## 8. 轻量化要求与下一步

基础运行不常驻训练模型，不默认启动后台线程或 worker，不加载全量轨迹、向量索引或训练数据。检索候选数、Token、批大小、并发数和缓存容量均可配置上限。后台任务与训练任务在独立进程中执行并支持背压和暂停。

资源验收分别测量冷启动、空闲 RSS、固定数据量检索峰值和后台整理峰值，报告操作系统、Python 版本、样本规模及并发数。尚未实测前不宣称达到具体内存指标。

已有 MVP 文档列出决策、结果、奖励和受控 Procedure 记录，近期测试也覆盖了部分扫描与预检功能。这些证据不足以证明本文整个闭环已完成；真实 PostgreSQL 端到端验收仍需补齐。未来实施以现有领域模型为起点，先做接口差距清单，再完成 P7a，避免另建一套平行记录系统。

本次仅更新设计，后续开发优先级为反馈可信关联、记忆候选生命周期、可比较的评测与策略更新。Agent 训练和运行编排保留为明确的最后阶段交付。
